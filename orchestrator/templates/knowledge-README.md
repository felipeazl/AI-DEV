# Knowledge base — {description}

What AiDW has learned about the systems of this context, in notes linked to each other. Open the **context folder** as
an **Obsidian vault** to browse the graph (the notes appear next to the policies and the guides, which they can cite
by `[[name]]`); in chat and in the agents, use `python aidw.py kb show|search`.

Map of everything: [[index]] (generated by `python aidw.py kb index`; do not edit by hand).

## The rule that matters most

**Each fact lives in one note only.** Whoever needs it points to it with `[[note-name]]`; they do not copy it. If two
notes say different things, one is wrong: check the code and fix the wrong one.

## The base describes, the rule decides

A note says **how the code is today**, including legacy that is off the standard — it is a fact, not a rule. Which
standard new code follows is decided by the team's code guide and the `policies/` (including how the guide compares to
the standard already established in each repository), never by a note alone. Team conventions and work rules do not
go into the base: they go to `shared/` or `policies/`.

## Note types

| Folder | `tipo` | One note per |
|---|---|---|
| `sistemas/` | `sistema` | system of `context.toml` (the file name is the key: `[systems.payments]` → `sistemas/payments.md`) |
| `componentes/` | `componente` | library, project or package shared between systems |
| `integracoes/` | `integracao` | contract between two sides: endpoint, message, enum, event, shared configuration, external service |
| `conceitos/` | `conceito` | domain term (what it is, business rules, the right term) |
| `normas/` | `norma` | law, regulation or standard the domain must follow (one document per note): version in force, what it requires, which system complies |
| `ambiente/` | `ambiente` | how to operate: hosts per environment, authentication, database, recipes, tools |
| `decisoes/` | `decisao` | durable business or architecture decision, with author and date |
| `demandas/` | `demanda` | closed demand (development, PR review, survey) |

## Format

```markdown
---
tipo: sistema
resumo: One line that says what it is — shows up in the index and in the `kb show` lists.
sistemas: [payments]
palavras-chave: [PAYMENT_API_URL, PaymentController, dbo.Order]
fontes: ["C:/Projects/Payments/ARCHITECTURE.md", "us-1234"]
atualizado: YYYY-MM-DD
---

# Payments

Short text, with [[links]] to what already has a note.
```

- **File name:** lowercase, hyphens, no accents, unique in the whole vault (outside the base too).
- **`resumo`:** required. **`fontes`:** required, except in `conceito` and `demanda` (`path:line`, document,
  demand or person with date). **`atualizado`:** the date of the last check. **`sistemas`:** keys of
  `context.toml`. **`evitar`** (conceito): terms not to use — they become the glossary. **`aliases`:** other names.
  **`palavras-chave`** (sistema, componente, integracao, norma, ambiente): identifiers, config keys, routes, tables and
  synonyms someone would type to find the note (5 to 15, exactly as in the code); they weigh in `kb search`.

## What goes in and what does not

- **Goes in:** a verified fact that serves the next demand — how it works, where it is, contracts, pitfalls,
  decisions. One line per fact, with the source.
- **Does not go in:** a hypothesis, a detail of a single delivery, a secret, a credential, personal or customer data.
- **Build, test and environment blocks** stay in `context.toml`; the system's note points there.
- **Repository documentation:** cite the path and summarize; do not copy.
- **Lists the graph already gives** (demands that touched a system): do not keep them by hand — the backlinks show
  them.

## Validate

`python aidw.py kb check` (it also runs in `context check`). It also warns about a note longer than 150 lines (split it
into linked notes) and a note not checked for more than 6 months (check it again in the code).

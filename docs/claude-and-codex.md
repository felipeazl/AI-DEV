# Claude Code and Codex

AiDW is an agentic development plugin **for Claude Code**. Claude Code is the main platform: AiDW runs in full there,
and every new feature is written for it.

> **On Codex, AiDW is only agents and skills.** `install --provider codex` delivers the `aidw-*` agents and the
> `aidw-*` skills and nothing else: **no permission rules, no hooks (guard), no profile, no per-agent MCP and no
> mods.** The demand flow runs through the agents and skills, but protection and configuration stay with your Codex.
> For real work, use Claude Code.

## Comparison

| | Claude Code | Codex |
|---|---|---|
| What `install` delivers | the `aidw` plugin (agents and variants, skills, commands, hooks), the `aidw-mods` plugin and AiDW's rules in `~/.claude/settings.json` | **only** the `aidw-*` agents (`~/.codex/agents/aidw-<name>.toml`) and the `aidw-*` skills (`~/.agents/skills`) |
| Calling the orchestrator | `/aidw:go`, `/aidw:survey`, `/aidw:exit`, `/aidw:done` | `$aidw-go`, `$aidw-survey`, `$aidw-exit`, `$aidw-done` |
| User commands | only `go`, `survey`, `exit`, `diff`, `done`, `knowledge`, `context` in the `/` menu; the workflow skills are hidden (`user-invocable: false`) | every `$aidw-*` skill shows up (Codex does not hide skills); `go`, `survey`, `exit` and `done` run only when called (`agents/openai.yaml`) |
| Agents | `aidw:<name>`, plus one variant per exception (model and effort pinned) | `aidw-<name>`, plus one role per exception (`aidw-<name>-<effort>`), model and effort pinned in each TOML |
| Models | aliases `opus`, `sonnet`, `haiku` (always the newest version) | exact IDs, the equivalent tier, among those enabled for the account |
| Workflows (`development`, `pr-review`, `survey`), QA, review | ✅ | ✅ (through the skills) |
| Open and resume a demand | ✅ | ✅ |
| A worktree per demand (also `--pr`) | ✅ | ✅ (the sandbox asks for approval on `worktree create`) |
| AiDW permission rules (force push, `reset --hard`, `.env`; the context's `ask` list) | ✅ `~/.claude/settings.json` | — your Codex's (its sandbox and approvals) |
| Guard: agent outside the worktree, commit with `AIDW-TEST` | ✅ plugin hooks | — |
| MCP and tools limited per agent | ✅ the subagent's `tools`/`disallowedTools` | — every agent sees the MCPs of your `~/.codex/config.toml` |
| Reminder after compaction, orchestrator-mode registry | ✅ plugin hooks | — |
| Mods: strip and panels, automatic metrics, delegation locks, secret filter | ✅ `aidw-mods` | — the orchestrator runs `record` itself |
| Moving the chat to the worktree, diff panel (`/aidw:diff`), session folders | ✅ | — (`aidw open --provider codex --demand <id>` opens in the worktree) |
| Browser | Claude in Chrome, the app's browser, Playwright | `@Chrome` and `@Browser` (app), Playwright (if it is in your Codex) |
| Project mode (a chat at the AiDW root) | ✅ `CLAUDE.md` | ✅ `AGENTS.md` (generated by `apply`) |

### Rule for new features

Every new feature starts on Claude Code. It goes to Codex only if it fits in an agent or a skill, without needing a
session, interface, hook or configuration feature of Codex. When it does not fit, it goes in the table above and Codex
goes without it: no partial equivalent is built just to keep parity.

## Using AiDW on Codex

```powershell
python aidw.py install --provider codex              # aidw-* agents and skills
python aidw.py open --provider codex --demand 1234   # the session in the demand's worktree
```

- **`multi_agent_v2`:** the orchestrator calls the agents with `spawn_agent`, which needs this feature.
  `aidw open --provider codex` passes `--enable multi_agent_v2`; if you open Codex another way, turn it on in your
  `~/.codex/config.toml` (`[features]` → `multi_agent_v2 = true`). `install` and `doctor` warn when it is missing.
- **Folders:** `aidw open` starts Codex in the demand's worktree (`-C`) and adds the AiDW folder (`--add-dir`), where
  the demand artifacts live. Writing anywhere else asks for the sandbox's approval.
- **Worktree:** `worktree create` writes to the repository's `.git`, which the Codex sandbox leaves read-only: approve
  that command. The agents do not commit (you do).
- **Protection:** without AiDW's rules and hooks, only Codex's approvals apply. Check commit, push, write SQL and every
  locked action carefully before approving.
- **MCPs:** the agents use the MCPs you registered in Codex (`codex mcp add …`), with no per-agent limit.
- **Metrics:** the orchestrator runs `aidw.py record --codex-task <task_name>`, which reads the sub-agent session's
  real token usage.

### Agents and effort

As on Claude, each variant is its own role: `~/.codex/agents/aidw-<name>.toml` is the default and
`aidw-<name>-<effort>.toml` (or `aidw-<name>-<model>-<effort>.toml`) each exception, every one with its model
(`model`, the Codex equivalent of its tier) and effort (`model_reasoning_effort`) pinned, plus the agent's
instructions. The orchestrator spawns the role named in its *Agents and effort* cell and never passes `model` or
`reasoning_effort` (another model only when you ask). The orchestrator in project mode (`aidw.py chat`) starts with
its configured model and effort.

### Old installs

Earlier installs put into Codex the `aidw` profile (`~/.codex/aidw.config.toml`), the rules
(`~/.codex/rules/aidw.rules`) and AiDW hooks in `~/.codex/hooks.json`. Today's `install --provider codex` removes all
three (in `hooks.json`, only AiDW's groups), and `doctor` warns if any is left.

## Native mode

The default (`[delegation] mode = "native"`). The agents are the CLI's own subagents:

- **Claude:** the `Agent` tool with the `subagent_type` from the table. Model and effort are pinned in the subagent
  file, hence the variants (`aidw:coder-medium`, `aidw:explorer-sonnet-high`). `omitClaudeMd` keeps the agent from
  loading the orchestrator's rules. Each role's tools and MCPs live in the subagent itself.
- **Codex:** `spawn_agent` with the agent type from the table (`aidw-coder`, `aidw-coder-medium`…), which needs `multi_agent_v2`.

After each subagent, the metric goes into `metrics.md`: on Claude the `aidw-mods` mod records it by itself (without it,
the orchestrator runs `aidw.py record`); on Codex the orchestrator runs `record --codex-task`.

## Headless mode

`[delegation] mode = "headless"`, project mode only: one process per task through `aidw.py delegate`, with
`claude -p --agents … --agent <name>` or `codex exec` with the definition on stdin (there, the role's MCPs and blocked
tools go through `-c`). Locked actions come back as `denials`. Meant for automation; the plugin requires native.

## Browser

- **Claude:** Claude in Chrome (your Chrome, already logged in) or the desktop app's browser; Playwright through MCP.
- **Codex:** in the desktop app, `@Chrome` (Codex's extension in your Chrome, logged in) and `@Browser` (the app's
  browser, for local and public pages); in the CLI, Playwright, if it is in your Codex.
- qa uses what it has; if the subagent cannot use any, it returns the criterion to the orchestrator, which tests it in
  its own browser and discusses the result with you.

## Codex limits

Besides what is Claude Code only (above):

- There is no tool to change the session folder or add one mid-conversation: `/aidw:diff` and the session folders do
  not exist there. `aidw open --provider codex` opens already in the worktree (with `--app`, in the desktop app).
- The worktrees the Codex app creates are its own (`$CODEX_HOME/worktrees`); the demand's are AiDW's and open through
  `aidw open`.
- If the `node` on your PATH lives in your user profile (e.g. nvm), the Codex sandbox cannot read it: install Node
  outside the profile (e.g. Program Files) for the builds.

## What is generated

None of this is versioned.

| File | Made by | Content |
|---|---|---|
| `.aidw/marketplace/plugins/aidw/` | `install` | The plugin: agents and variants, skills, `go`/`survey`/`exit`/`diff`, references, hooks |
| `.aidw/marketplace/plugins/aidw-mods/` | `install` | The Claude Code mods, copied from `mods/aidw-mods` (without the tests) with this machine's AiDW root |
| `.aidw/install-manifest.json` | `install` | What install added in Claude and Codex (so `uninstall` removes only that) |
| `~/.claude/settings.json` (merge) | `install` | `deny`/`ask`/`allow` rules, allowed folders and `env`, only AiDW's items |
| `~/.codex/agents/aidw-*.toml`, `~/.agents/skills/aidw-*` | `install --provider codex` | Agents and skills — and only that |
| `state/worktrees.json`, `state/sessions.json` | commands and hooks | The worktree registry and the sessions in orchestrator mode |
| `.aidw/agents/<name>.md`, `.aidw/reference/`, `.aidw/runtime.json` | `apply` | Each agent's definition, the orchestrator's references, the resolved configuration |
| `CLAUDE.md`, `.claude/agents/`, `.claude/settings.local.json`, `.claude/skills/`, `.mcp.json` | `apply` (Claude) | Claude's project mode |
| `AGENTS.md`, `.codex/config.toml`, `.codex/agents/`, `.codex/rules/aidw.rules`, `.agents/skills/` | `apply` (Codex) | Codex's project mode (only with `provider = "codex"`, at the AiDW root) |

Guarantees: everything is validated before writing; with no change, nothing is written; only files generated by AiDW
are removed; a generated file edited by hand stops `install` (unless `--force`).

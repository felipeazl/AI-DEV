# Skills

A **skill** is a Markdown procedure (`SKILL.md`) an agent follows when the step calls for it: how to write a plan, how
to review a diff, how to handle a database operation. Skills make behavior **repeatable**: the same steps on every
demand, without relying on the model to remember.

## Kinds

| Kind | How to tell | Who calls it | Examples |
|---|---|---|---|
| **Admin (direct use)** | frontmatter `aidw: admin` | you, any time, also outside a demand | `context`, `done`, `knowledge` |
| **Generated by the plugin** | written by `install` | you | `go`, `survey`, `fix`, `ask`, `investigate`, `card`, `kb-review`, `exit`, `diff` |
| **Workflow** | all the others (`user-invocable: false` in the plugin: hidden from the `/` menu) | the orchestrator or an agent, when the step calls for it | `to-spec`, `code-review` |

A workflow skill is valid **only inside a demand** run by the orchestrator; its description starts with
`[AiDW] Only inside a demand run by the AiDW orchestrator.` so Claude does not use it elsewhere.
`disable-model-invocation: true` keeps the model from calling a skill by itself (`go`, `survey`, `fix`, `ask`, `investigate`,
`card`, `kb-review`, `exit` and `done` run only when you call them).

## The core skills

### You call

| Skill | What it does |
|---|---|
| `go [demand]` | Takes over the chat as the orchestrator: detects the project, opens or resumes the demand, creates the worktree and drives the flow. `pr <n>` reviews someone else's PR |
| `survey <card or text>` | Survey before implementing, read-only ([workflow.md](workflow.md#survey-survey)) |
| `fix <demand> <what>` | The full orchestrator started on the short path of a demand that already has code: a bug the QA returned (`bug <n>`), the PR's comments (`pr`) or an adjustment |
| `ask <question>` | A question about the code, a contract or the environment; the explorer answers with `file:line` (`answer-<id>.md`). Lean prompt: only the explorer, read-only |
| `investigate <evidence>` | The root cause of an error, log or record in a wrong state (`investigation-<id>.md`) and, if it is a defect, the Bug or technical debt drafted by the documenter. Lean prompt: explorer and documenter |
| `card <idea or problem>` | A User Story or technical debt grounded in the code (`workitem-<id>.md`), created only with your OK of the fields. Lean prompt: explorer and documenter |
| `kb-review [scope]` | Rechecks the knowledge base against the code (`kb check` and the oldest notes) and updates the notes with your OK. Lean prompt: only the explorer |
| `exit` | Records the step and the next action (`paused`) and returns the chat to normal |
| `diff [repo\|exit]` | Claude only. Moves the session to a demand repository's worktree; the diff panel follows ([demands-and-worktrees.md](demands-and-worktrees.md#see-each-repositorys-diff)) |
| `done` | Closes the task: starting from `kb collect`, writes into the context only what was verified and matters for the next demands — the demand's note and the knowledge notes it touched, linked without duplicating; build and environment in `context.toml` —, validates, reinstalls, commits and pushes the context repository, marks the demand `done` and leaves orchestrator mode. Never writes a secret or personal data |
| `knowledge [topic]` | What the context's knowledge base knows about a system, contract, concept or demand (`kb show` + `kb search`), following links only as far as the question needs; fixes or completes a note when you ask ([contexts.md](contexts.md#knowledge-base)) |
| `context` (`list`, `use <name>`, `create`) | Lists the contexts (also with no argument), activates one, or creates a new one from an analysis of the repositories and at least 10 questions ([contexts.md](contexts.md#create-a-context)) |

### The workflow calls

| Skill | Used by | What it does |
|---|---|---|
| `to-spec` | planner (preloaded) | Checks existing work, starts from the exploration reports, inspects dependencies, describes current behavior from the code and writes the spec-driven plan with deliveries `E1…`, self-contained for the coder |
| `verify-premise` | orchestrator, planner, reviewer | Before accepting "it can't be fixed here", "this covers every case", "it's the repo's convention", "that value never happens": first-hand evidence, or the premise falls |
| `prepare-worktree` | orchestrator, coder | Creates, inspects and removes the demand's worktree with `aidw.py worktree`: right base, branch, junctions, registry; also the read-only worktree of someone else's PR |
| `code-review` | reviewer (preloaded) | One-pass review against the plan — quality, bugs with a failure scenario, security with an attack path —, findings with stable IDs, severity, category and a keep/discard recommendation |
| `database-safe` | explorer, qa | Classifies each database operation: reads only through the validator; writes always proposed with the exact statement, the check query and the rollback |

Old names (`verificar-premissa`, `preparar-worktree`) in a config or context still resolve to the new ones.

## `skills` × `preload`

Each agent has two lists (in `aidw.config.toml` and in `context.toml`):

- **`skills`:** the ones it **may** load. They appear as a short list of names and paths; the content enters only when
  it uses the skill.
- **`preload`:** a subset injected **whole** at the start of every run, for what the agent always uses (the reviewer
  always reviews, so `code-review` comes loaded). Every `preload` skill must also be in `skills`.

Preloading what is not always used only raises the cost of every delegation.

## Context skills

A context can bring its own skills in `contexts/<name>/skills/<skill>/SKILL.md`: read a card from the team's board in
cheap steps, attach a file, build QA's test plan, draft a story in the company's format. They go into the same plugin
and are given to an agent through `skills = [...]` in `[agents.<role>]` of `context.toml`. A context skill with the same
name as a core skill replaces it (with a warning).

## Write a skill

```markdown
---
name: my-skill
description: What it does and WHEN to use it, in one sentence. This is what the model reads to decide.
---

# my-skill

1. A concrete step, with the exact command or tool.
2. Where to write the result.
3. When to stop and return a question.

## Rules

- What never to do.
```

Good practices:
- **The `description` decides everything:** say what the skill does and its trigger.
- **Short, verifiable steps**, with exact commands. Not "analyze carefully".
- **Stop at the first sufficient answer:** layered procedures (read the field, only then the relations, only then the
  attachments) save tokens.
- For direct use, outside a demand, add `aidw: admin` to the frontmatter.

To enable it:
1. Save it as `skills/<name>/SKILL.md` (core) or `contexts/<ctx>/skills/<name>/SKILL.md` (context).
2. Add the name to the agent's `skills = [...]` (and to `preload`, if it always uses it).
3. `python aidw.py install` (and `apply` for project mode), and a new chat.

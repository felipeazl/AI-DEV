# Security

The principle: **the model is never the last barrier.** A prompt instruction can be forgotten, misread or bypassed by a
text in the code or on a card. So what is risky is blocked by mechanisms the model does not control.

## Layers

Every layer below belongs to **Claude Code**. On Codex, AiDW installs only agents and skills: no rules, no guard, and
only Codex's own approvals and sandbox apply ([claude-and-codex.md](claude-and-codex.md)).

| Layer | How it works |
|---|---|
| **Global CLI rules** | `install` writes into `~/.claude/settings.json`: `deny` for force push, `reset --hard`, `clean -f` and reading `.env` (the default `[policies] deny`); `ask` for what your `[policies] ask` and the context's `ask`/`git_ask` list (typically commit, push, merge, rebase, checkout, write SQL); `allow` only for routine (the `aidw.py` commands, the context's `allow`). They apply in **every** session, with or without the orchestrator |
| **Guard (hook)** | An AiDW agent cannot edit the main working copy of a repository that has an active demand worktree; the main conversation stays free. Shell commands are not checked (tasks point only to the worktree), with one exception: `git commit` in a demand worktree that still has a test adjustment (`AIDW-TEST`) is refused, for any session |
| **Worktree** | The demand's code stays out of your working copy; `worktree remove` refuses a worktree with local changes or unpushed commits |
| **Per-agent scope** | Each role has only the tools and MCP servers it needs (`tools`/`disallowedTools` of the subagent). The context can block tools per role (e.g. only the orchestrator comments on a card, after your OK) |
| **Context validators** | Risky operations go through scripts that refuse what is not allowed (e.g. read-only SQL, run inside a `ROLLBACK`) |
| **Locked action → proposal** | An agent that needs a locked action returns the exact command or text with `policy_requires_approval`; the orchestrator batches the proposals and asks your OK once. A denial is never worked around with another tool, script or command |
| **Delegation locks (mod)** | `aidw-mods` refuses a delegation with an unexpected `subagent_type`, a `model` you did not ask for, a missing demand folder or a pasted input ([mods.md](mods.md#delegation-locks)) |
| **Secret filter (mod)** | Tool results are masked before they enter the conversation: only the secret's name and length remain ([mods.md](mods.md#secret-filter)) |
| **Private contexts** | The context repository is its own and ignored by AiDW's Git; `doctor` and `context check` fail if it stops being so |
| **Secrets** | Never in a file, log, plan, review or comment. `doctor` only checks that variables exist; `context list` shows the remote only by host |

## Core policies

In `orchestrator/policies/`, for the orchestrator and every agent:

| Policy | Summary |
|---|---|
| `git.md` | Never force push; never delete protected branches; never merge without review and human approval; never rewrite published history; a feature branch per spec |
| `database.md` | Production is read-only; destructive operations need approval; migrations validated outside production; generated SQL goes through `database-safe` |
| `production.md` | No deploys, restarts, config or data changes in production without approval; an unknown environment is treated as production |
| `secrets.md` | Never print secrets; never read `.env`; reference secrets only by variable name |
| `permissions.md` | The CLI enforces the rules generated by `apply`/`install`; what needs approval comes back as a denial and is proposed |

The context adds the team's own (approvals, allowed environments, board writes, scope).

## When you approve

The flow runs on its own for routine work (reading code, planning, delegating, builds, tests, local git). You approve:

- the git operations your context marks as `ask` (usually `commit`, `push`, `pull`, `merge`, `rebase`, `reset`,
  `checkout`/`switch`, `cherry-pick`, `revert`, `tag`, deleting a branch);
- write SQL and anything else the context marks;
- state-changing API calls;
- comments on a card or PR (the pending items for QA go in the PR OK; on someone else's PR, in the final review);
- anything in your or the context's `ask` list.

The CLI's permission prompt is the approval point.
